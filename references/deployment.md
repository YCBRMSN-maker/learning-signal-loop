# 多服务容器化部署

目标：**一条命令拉起全栈**，并把所有慢操作移出请求链路。

## 服务拓扑

| 服务 | 职责 | 说明 |
| --- | --- | --- |
| `redis` | 消息 broker + 缓存 | Celery broker/backend，同时承载部分学生状态 |
| `backend` | FastAPI 主服务 | 对外提供 API，处理同步请求 |
| `celery-chat-worker` | 异步问答 | 队列 `chat_queue` |
| `celery-submit-worker` | 提交预检 | 队列 `submit_queue`，跑沙箱 |
| `celery-db-worker` | 集中写库 | 队列 `db_writer_queue` |
| `celery-behavior-worker` | 行为处理 | 队列 `behavior_queue` |
| `celery-beat` | 定时调度 | 周期性任务 |
| `frontend` | nginx | 静态资源 + API 反向代理，同时提供学生端与教师端入口 |

依赖关系：所有 worker 与 backend 都依赖 `redis`；worker 再依赖 `backend`，保证启动顺序。

对外端口：后端一个端口；前端一个容器暴露两个端口——学生端与教师端各一个；Redis 默认不对外映射，仅容器内互访。

## 队列分工与并发模型

拆多个队列的意义：**不同任务的瓶颈不同，混在一个队列会互相阻塞**。

| 队列 | 任务特征 | 并发模型 | 理由 |
| --- | --- | --- | --- |
| `chat_queue` | 调大模型，等待网络 | `prefork` | 调用多为阻塞等待，隔离性好 |
| `submit_queue` | 跑无头浏览器，CPU + 内存重 | `prefork` | 需要强隔离，防止互相影响 |
| `db_writer_queue` | 高频小写入 | `gevent`（并发高） | IO 密集，协程切换成本远低于进程 |
| `behavior_queue` | 行为事件解释 | `prefork` | 单条处理快，隔离优先 |

要点：

- **IO 密集用 gevent，CPU/隔离型用 prefork**。用反了会让吞吐量骤降或内存爆炸。
- 沙箱类任务**必须与请求链路隔离**，否则一个死循环的学生提交就能拖垮整个 API。
- 队列名集中定义，任务路由在一处声明，避免散落。

## 持久化设计

| 卷 | 挂载点 | 为什么需要 |
| --- | --- | --- |
| `backend_data` | 后端与所有 worker 的数据库目录 | **一致性关键**：容器重建后数据不丢，且多 worker 读写同一份 |
| `redis_data` | Redis 数据目录 | 缓存与队列状态持久化 |
| `archive_data` | 归档文件目录 | 用户"存入历史资料"的文件需跨容器重建保留 |

**最关键的一条**：所有 Celery worker 都必须挂载 `backend_data`。漏掉任何一个，症状是"异步任务写进去了，但接口读不到数据"——非常难排查，因为两边都不报错。

## 镜像构建

**后端镜像**：Python slim 基础镜像 → 系统依赖（含无头浏览器所需的图形库）→ Python 依赖 → 装 Playwright 浏览器 → 启动命令。

- 容器内没有 GPU 时，**先装 CPU 版 torch**，避免拉取一堆 CUDA 包（体积差十倍以上，构建时间差很多）。
- Playwright 浏览器下载走国内镜像源，否则构建极易卡死。

**前端镜像**：Node alpine 基础镜像 → 构建前端产物 → nginx 托管。

**国内网络环境优化**（构建稳定性的关键，不做会卡到怀疑人生）：

- 系统包源换国内镜像（含 security 源）
- Python 包源换国内镜像，必要时给 PyPI 配备用源
- npm 换国内镜像
- Playwright 浏览器下载换国内镜像

## 前端 nginx 职责

一个 nginx 承担四件事：

1. **静态资源服务**（前端产物）
2. **SPA fallback**：前端路由回退到入口 HTML
3. **API 反向代理**：把 `/api/v1/` 转发到后端服务，避免跨域
4. **WebSocket 代理**：流式问答需要长连接，必须单独配置代理升级头

多端入口（学生端 / 教师端）通过**不同端口或路径前缀**区分，共用同一个 nginx 与后端。

## 工程亮点（可用于陈述）

1. **异步削峰**：四类慢操作分队列处理，并发模型按任务特征选择，慢操作不阻塞请求链路
2. **沙箱隔离**：学生代码在独立 worker 的浏览器沙箱内执行，与主服务进程隔离
3. **多 worker 共享数据库**：从部署层面杜绝"任务写进去、接口读不到"的不一致
4. **一键部署**：一条 compose 命令拉起全栈，含 Redis、后端、多 worker、定时任务与前端
5. **离线产物 + 在线轻计算**：情绪模型与聚类中心都是构建期/离线产物，在线只做前向计算，保证响应延迟

## 怎么验收

- [ ] 一条 compose 命令能把全部服务拉起，且容器不反复重启
- [ ] 后端健康检查通过，接口文档可访问
- [ ] 学生端与教师端两个入口都能打开
- [ ] 提交一次异步任务，在对应队列 worker 的日志里能看到任务被消费
- [ ] 提交一次答题，接口能立刻读到刚写入的结果（验证多 worker 共享数据库）
- [ ] 重启容器后，历史数据与归档文件仍在

## 常见坑

| 症状 | 原因 |
| --- | --- |
| 异步任务写入了但接口读不到 | 某个 worker 漏挂数据库卷，与后端不是同一份数据 |
| 后端连不上 Redis，登录失败 | Redis 容器没接入同一 Docker 网络，容器名解析不到 |
| 前端改了样式但页面没变 | 静态资源被长期缓存，需对 CSS/JS 设 `no-cache` |
| 构建卡在拉取依赖层动辄十几分钟 | 没换国内镜像源 |
| 构建失败且重试无效 | 命中损坏的构建缓存，需清理卷与缓存后重建 |
| 并行构建多个镜像导致网络拥塞 | 改为逐个构建，或先构建最关键的后端镜像 |
| compose 命令找不到配置文件 | 文件名非默认时必须显式指定 `-f <文件>` |
| 改了后端代码但容器行为没变 | 容器用的是镜像快照，源码改动未进入镜像 |
