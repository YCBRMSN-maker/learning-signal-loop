# 技术详解

每项按「解决什么问题 → 核心做法 → 关键参数 → 实现要点 → 怎么验收 → 常见坑」展开。

以下全是**通用原理**，可直接搬到同类校园教学系统，不含任何仓库路径。

本文件的覆盖范围分三档，注意区分：

| 档 | 章节 | 定位 |
| --- | --- | --- |
| **五个支撑技术** | 1–5 | 直接服务于两个主线场景（学生答疑 / 教师学情研判），是功能实现的主体 |
| **沙箱预检** | 6 | 闭环的**信号源头**，属基础设施，不是独立场景 |
| **容器化部署** | 7 | 工程侧，与教学功能正交 |

五个支撑技术依次为：情绪识别、学习状态聚类、BKT 知识追踪、RAG 知识增强、行为采集与解释。

## 1. 情绪识别

**解决什么问题**：学生已经沮丧了，系统还在讲更难的题，体验直接崩塌。情绪是"当下状态"，比掌握度更即时。

**核心做法**：本地 BERT 系模型对输入文本做序列分类，softmax 取最大概率，输出情绪标签与置信度。

**关键参数**

| 项 | 值 |
| --- | --- |
| 输出类别 | `NEGATIVE` / `NEUTRAL` / `POSITIVE` |
| 模型 | `BertForSequenceClassification` 或 `DistilBert` |
| 部署形态 | 本地模型，进程内推理，不走外部 API |

**实现要点**

- **必须做降级**：启动时检查本地模型目录是否存在且可加载，失败则跳过情绪识别而不抛异常。情绪识别是"增强项"，不能因为它缺失就把整条问答链路拖垮。
- 输出带**置信度**，低置信度时不要过度干预教学策略。
- 情绪结果要和判题结果联动，才能识别**挫败**：连续答错 + 情绪为负 → 判定挫败，触发鼓励或降难度。
- **冷启动**：不要拿广泛领域的通用中文情绪语料直接微调，语言分布与校园教学场景不匹配，教学场景表现会明显低于跑分。应取本场景真实日志做 few-shot 种子 + 人工验收集。判据、种子样本与标注方式见 `references/emotion-labeling-seed.md`。
- **对内四类、对外三类**：内部建议保留 `NEUTRAL / CONFUSED / FRUSTRATED / POSITIVE` 驱动干预——「不懂」要换讲法，「不对」要先安抚，两者干预方式完全不同；对外再合并为积极/中性/消极三分类用于统计与汇报。

**怎么验收**：临时移除或改名情绪模型目录，重启后问答链路应仍然可用（降级生效）；输入明显负面文本，标签应为 `NEGATIVE`；用人工盲标的留出集比对标注一致率。

**常见坑**

- 把情绪识别写成硬依赖，模型缺失导致整个服务起不来。
- 只识别不消费——识别出来却没人读，等于没做。
- 只用单条消息判情绪，不看连续失败次数，误判率高。
- **训练数据类别极不均衡**会导致模型坍缩为"永远输出同一个标签"。若出现"任何输入都判同一类"，先查各类样本占比，再查标注质量。
- 把「X 是什么」这类主动求知标成消极——会把学习动机最强的学生标成情绪最差。
- 把系统拼进"用户消息"里的题目描述、代码片段、判题结果当成学生输入来标注。

## 2. 学习状态聚类

**解决什么问题**：面对一个学生，不知道该按"基础巩固 / 正常推进 / 拔高拓展"哪一档讲。聚类把连续、高维的行为特征离散成可操作的教学档位。

**核心做法**：**离线训练聚类中心，在线只算距离归类。**

- 离线：编码对话消息 → 窗口池化 → 降维 → 归一化 → 训练聚类中心，产物落盘
- 在线：同样的特征工程 → 与各聚类中心算余弦距离 → 取最近类

**关键参数**

| 项 | 值 |
| --- | --- |
| 编码器 | SentenceTransformer |
| 特征工程 | 窗口池化 → PCA 降维 → L2 归一化 |
| 类别语义 | `Normal` / `Advanced` / `Struggling` |
| 输出字段 | `cluster_id` / `cluster_name` / `progress_score` / `confidence` |
| 落盘产物 | 聚类中心、PCA、结构特征标准化器、类别名映射、进度分 |

**实现要点**

- **不要每次请求跑一次聚类算法**。在线跑 KMeans 既慢又不稳定（同一学生两次结果可能不同）。离线训练中心 + 在线算距离，延迟低且结果稳定。
- 特征工程必须**离线与在线完全一致**，否则距离算出来没有意义。建议把特征工程抽成一个函数，两侧复用。
- 三个类别名要有明确的教学含义，直接映射到教学策略，否则聚类结果没法用。

**怎么验收**：能返回类别名、进度分与置信度三件套；用明显不同水平的历史对话测试，分类结果应有区分度；同一输入重复调用，结果应稳定一致。

**常见坑**

- 在线实时聚类，延迟高且结果抖动。
- 距离计算与训练时的特征处理不一致（漏了归一化或降维），导致分类随机。
- 聚类类别没有映射到教学动作，聚了等于没聚。

## 3. BKT 知识追踪

**解决什么问题**：判断某个知识点学生到底会不会。答对一次不代表会（可能是猜的），答错一次也不代表不会（可能手滑）。

**核心做法**：贝叶斯知识追踪。由答题对错算观测概率，更新后验掌握概率，再叠加学习转移概率。

**关键参数**

| 参数 | 含义 | 默认值 |
| --- | --- | --- |
| `p_init` | 初始掌握概率 | `0.2` |
| `p_transit` | 每次练习后学会的概率（学习率） | `0.15` |
| `p_slip` | 已掌握却答错的概率（失误率） | `0.1` |
| `p_guess` | 未掌握却答对的概率（猜对率） | `0.2` |

**实现要点**

- 四个参数要**可配置**，不要写死在函数里——不同知识点难度差异很大。
- 更新时机是**判题结果回写时**，不是每次聊天都更新。聊天不产生对错信号，更新会污染掌握度。
- 掌握概率要**持久化**（Redis 或数据库），否则重启即丢，学习路径会跳变。
- 掌握度是消费方的输入：学习路径推荐、知识点排序、提示词中的难度选择。

**怎么验收**：连续提交"答对"若干次，掌握概率应单调上升并趋近上限；连续"答错"应下降；重启服务后掌握度不丢失。

**常见坑**

- 每次对话都更新掌握度，导致数据失真。
- 参数写死，换科目就失效。
- 不持久化，重启后学生"归零"。
- 只在答对时更新，忽略答错的分支。

## 4. RAG 知识增强

**解决什么问题**：大模型对课程专有知识会编造。RAG 把真实知识片段喂进提示词，让回答有据可依。

**核心做法**：文档切分 → 向量化 → 建近似最近邻索引；查询时把问题向量化 → 召回 top-k 片段 → 拼接进提示词。

**关键参数**

| 项 | 值 |
| --- | --- |
| 切分大小 | `chunk_size = 500` |
| 切分重叠 | `chunk_overlap = 50` |
| 向量维度 | `2560` |
| 索引类型 | 近似最近邻（如 Annoy / FAISS） |
| 召回数 | top-k |

**实现要点**

- **改了知识库必须重建索引**。这是最高频的坑：文档更新了但索引没重建，召回永远是旧内容。
- 切分要留**重叠**（50 字符），否则答案正好被切在边界上，召回片段语义不完整。
- 查询文本可**先做翻译再取向量**：中文提问对英文知识库召回效果差，中间加一层翻译能明显提升召回率。
- 索引与原始 chunk 文本要一起持久化，召回后需要拿回原文。

**怎么验收**：改一条知识库文档 → 重建索引 → 同一个问题，召回结果应随之变化；提问一个只有知识库里有答案的问题，回复应引用到相关内容。

**常见坑**

- 改文档不重建索引（最高频）。
- chunk 过大导致召回片段噪声多，过小导致语义割裂。
- 索引维度与 embedding 模型输出维度不一致，直接报错或召回全错。
- 召回结果不截断，把 top-k 全部塞进提示词，浪费上下文还稀释重点。

## 5. 行为采集与解释

**解决什么问题**：情绪识别只看单条消息，看不出"卡壳"——卡壳是**一段时间内的连续失败**，必须靠行为事件累积才能判定。它是情绪识别与聚类的共同信号来源。

**核心做法**：前端静默上报事件 → 后端按事件类型分发解释 → 结果写入学生画像。

- **采集**：前端上报页面停留、代码编辑、测试提交、AI 求助、空闲等事件（代码编辑做 2 秒防抖，避免高频刷量）
- **解释**：事件分发表把不同事件映射到不同处理逻辑；测试提交触发掌握度更新与挫败检测
- **消费**：解释结果写入学生画像，供情绪识别、聚类、提示词组装读取

**关键参数**

| 项 | 值 |
| --- | --- |
| 空闲判定阈值 | 60 秒无活动视为空闲 |
| 空闲提示延迟 | 进入空闲后再等 15 秒才提示 |
| 提示全局冷却 | 10 分钟（避免反复打扰） |
| 挫败检测窗口 | 2 分钟 |
| 挫败错误率阈值 | 0.75 |
| 挫败检测间隔 | 10 秒 |
| 情绪权重档位 | 负面情绪按强度三档累加（0.1 / 0.2 / 0.3） |

**实现要点**

- 事件用**异步**方式落库与解释，不能阻塞学生请求。
- 事件类型要**可扩展**：新增行为只加分发项，不改主流程。
- **跨事件累积**才是关键：单条"答错"不构成挫败，窗口内错误率超阈值才判挫败。
- 提示要**不打断正在输入的学生**：编辑类活动应豁免空闲计时。

**怎么验收**：上报一条测试提交，画像应随之更新；在窗口内连续提交错误答案，应触发挫败标记；学生持续空闲到阈值，应出现主动提示，且正在编辑时不触发。

**常见坑**

- 同步上报，阻塞学生请求。
- 只看单条事件判定状态，忽略时间窗口，误判率高。
- 事件类型写死在分发逻辑里，新增行为要改主流程。
- 空闲提示不设豁免，学生在编辑器里打字时被打扰。

## 6. Test Assist 沙箱预检（基础设施 · 信号源头）

> 不属于上述五个支撑技术：它不直接服务某个场景，而是为整条闭环提供**对错信号**。没有它，掌握度无从更新。

**解决什么问题**：学生的代码或页面作业没法自动判，人工看不过来；同时学生代码绝不能直接跑在宿主机上。

**核心做法**：无头浏览器（Playwright + Chromium）加载学生提交的页面，注入其 CSS/JS，等页面就绪后**逐条执行检查点**，收集通过/失败结果。

**关键参数**

| 项 | 说明 |
| --- | --- |
| 执行环境 | Playwright + Chromium 无头浏览器 |
| 页面模式 | raw HTML 模式 / 标准模板模式 |
| 判定单元 | 检查点列表（checkpoints） |
| 输入 | 用户代码、检查点列表、知识点 ID |
| 输出 | 通过状态 + 失败详情 |

**实现要点**

- **执行必须在沙箱内**，禁止在宿主机直接运行学生代码，这是安全红线。
- 检查点要**逐条判定并记录失败详情**，不能只返回一个总的"不通过"——失败详情才是学生改进的依据，也是回写掌握度的信号来源。
- 按任务类型选择模式：纯 HTML 提交走 raw 模式，基于模板的走标准模式。
- 判题结果要**回写掌握度与情绪状态**，形成闭环，否则判题只是一次性输出。

**怎么验收**：故意提交死循环或危险代码，宿主机不受影响、沙箱有超时保护；提交一份正确的实现，检查点应全部通过；故意改错一处，应精确定位到对应检查点。

**常见坑**

- 没有超时保护，学生死循环把浏览器进程拖死。
- 只返回总结果，不返回失败详情，学生不知道错在哪。
- 判题结果不回写掌握度，闭环断掉。
- 页面还没加载完就开始检查，出现随机失败（需等待就绪信号）。

## 7. 多服务容器化部署（工程侧 · 与教学功能正交）

> 不属于上述五个支撑技术，与教学功能正交。完整内容见 `references/deployment.md`，要点速览：

- 后端 + 多队列 worker + Redis + 前端 nginx，一条 compose 命令起全栈
- 慢操作全部异步化，不同队列用不同并发模型
- 所有 worker 共享同一数据库卷，否则"任务写进去、接口读不到"
- 前端 nginx 承担静态资源、SPA fallback、API 反向代理、WebSocket 代理
